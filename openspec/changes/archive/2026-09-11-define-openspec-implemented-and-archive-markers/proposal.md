## 2. 背景与目标

审计发现当前状态判定的三个问题:

1. **无显式生命周期状态**。历史 change 普遍没有统一状态字段，无法直接区分待审核、实施中、已实施、已取消或已取代。
2. **归档与实施完成混淆**。2026-08-13 已执行历史批量归档，但其中部分 change 没有显式状态或 `summary.md`，不能仅凭归档位置推断已经实施。
3. **完成证据缺少统一门禁**。现行规则要求执行 `summarize`，但没有明确 `summary.md`、验证结果、阻塞项与 `R0/R1/R2/R3` verdict 之间的关系。

目标:

- 明确定义提案生命周期的六个状态。
- 明确定义"已实施"的硬性要求，必须包含 `summary.md`。
- 明确定义归档前置条件，并允许对 War3 客户端验收做显式豁免。
- 规范归档目录命名与归档语义，解释 2026-08-13 批量归档的历史边界。
- 让历史与未来的 change 都能用同一套规则自洽判定状态。

## 4. 方案摘要

在 `AGENTS.md`、`openspec/README.md`、模板与检查清单中新增以下约定:

### 4.1 提案生命周期状态

定义以下六个状态，并在 `proposal.md` 的基本信息中显式记录：
- `待审核`：提案已提交，等待用户批准。
- `已批准`：用户已批准，尚未开始实施。
- `实施中`：正在进行代码编写或文档修改。
- `已实施`：变更已完成实施、验证与总结。
- `已取消`：提案被放弃，不再实施。
- `已取代`：提案被新的提案替代。

### 4.2 实施完成（已实施）的硬性要求

一个变更要标记为 `已实施`，必须同时满足以下条件：
1. 批准的变更范围已全部完成。
2. 要求的验证（如测试、构建、静态检查）已全部通过。
3. 实施后总结已完成，且必须在 change 目录下存在 `summary.md`。
4. 无阻塞性未完成项。

`R0/R1/R2/R3` 证据和 verdict 用于支持验证，但绝不能替代 `summary.md`。

### 4.3 归档前置条件与规则

1. 归档位置（`openspec/changes/archive/`）表示变更已关闭且不再活跃，并不等同于已实施。
2. 状态为 `已实施` 的变更，在满足上述实施完成要求后可以归档。
3. 状态为 `已取消` 或 `已取代` 的变更，只要在 `proposal.md` 中记录了关闭原因，即可直接归档，不要求提供 `summary.md`。
4. 归档目录命名规范：`openspec/changes/archive/<yyyy-MM-dd>-<change-id>/`，日期使用归档当天。
5. 若已批准提案的验证计划包含真实 War3 客户端验证，该验证默认是阻塞的。只有在审核阶段显式声明为非阻塞，并在 `summary.md` 中记录未执行原因与剩余风险时，才允许推迟该验证并归档。

### 4.4 2026-08-13 批量归档历史边界

2026-08-13 批量归档的变更属于历史清理。这些变更中未显式标注状态或缺失 `summary.md` 的项，未经过逐一验证，不能作为当前项目状态的证据。

## 5. 非目标

- 不修改提案等级、工件矩阵或实施后复盘强度规则。
- 不批量改写或补写历史已归档 change 的 `summary.md`。
- 不引入除六个状态外的其他生命周期状态。
- 不引入额外的元数据格式。
- 不调整本机 `.git/info/exclude` 对 `openspec/` 的追踪策略；需要提交时另行核对归档文件的 Git 跟踪状态。

## 6. 风险与回滚

- 风险: 归档豁免条款被滥用（以"客户端未验收"为由提前归档未完成 change）。
  - 控制: 豁免必须显式注明，且不能掩盖 tasks.md 未处置项；"无阻塞性未完成项"仍是硬条件。
- 回滚方式: 删除或还原相关文档与模板的修改，不影响任何代码。
