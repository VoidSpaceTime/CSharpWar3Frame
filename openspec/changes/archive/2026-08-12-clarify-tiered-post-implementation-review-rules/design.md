# 设计：分级实施后复盘治理

## 三层模型

### 第一层：OpenSpec 提案等级

提案等级由影响范围、风险、可逆性、公共契约和跨项目程度决定，继续控制提案工件、用户审核范围与总结深度。范围扩大时仍必须升级提案等级、补齐工件并重新提交审核。

### 第二层：实施后复盘强度

复盘强度控制 `test` 阶段需要覆盖多少风险视角，不替代直接测试、构建、静态检查或文档验证。

有序等级为：`R0 Direct < R1 Focused < R2 Targeted < R3 Comprehensive`。

- `R0`：直接验证。
- `R1`：在 `R0` 基础上完成 1 个技术准确性视角，提供证据和 verdict。
- `R2`：在 `R0` 基础上完成 2-3 个不同风险视角，分别提供证据和 verdict。
- `R3`：在 `R0` 基础上覆盖目标/约束、技术质量、安全、QA、上下文五类视角。

最终强度计算原则：

`final review intensity = max(default by proposal level, risk escalation, explicit user intensity requirement)`

计数单位是独立风险视角，不是代理数量或工具调用次数。一个执行者或工具可以覆盖多个视角，但每个视角必须独立给出证据与 verdict；重复同一视角不重复计数。

### 第三层：工具启用

Oracle、`review-work`、QA agent 等只是完成复盘目标的执行工具，不定义强度本身。

- `R1` 技术准确性复核优先使用 Oracle；不可用时允许等价复核并记录原因。
- `R2` 根据风险选择合适工具，不绑定固定代理名单。
- `R3` 要求五类视角完整，但不自动授权完整 `review-work`。
- 只有用户明确要求“全面复盘”“完整 QA”或直接指定 `review-work` 时，才启用完整 `review-work`；更高优先级指令要求时例外。

## 默认强度矩阵

| 提案等级 | 直接验证 | 默认专业复盘 | 完整五路 |
| --- | --- | --- | --- |
| `fast` | 必须 | `R0 Direct` | 不使用 |
| `light` | 必须 | 默认 `R0`；复杂、版本敏感或技术事实不确定时 `R1` | 不使用 |
| `full` | 必须 | `R2 Targeted`，按风险选择 2-3 路 | 不因等级自动使用 |
| `architecture` | 必须 | `R3 Comprehensive` | 必须覆盖五类视角 |

`light` 的 `R1` 路径只适用于变更仍满足 `light` 边界的情况。如果复杂度已经涉及公共契约、跨项目影响或其他 `full/architecture` 条件，必须先升级提案等级并重新审核。

## 风险强度判定

### 至少进入 R2 的风险

以下风险用于选择 2-3 路专项复核，但不会仅因名称自动进入 `R3`：

1. 公共 API 或对外行为契约。
2. Source Generator 输出契约。
3. 配置格式、构建链或发布契约。
4. 持久化、迁移、数据兼容性或数据丢失可能性。
5. 性能、资源、实时性或大规模数据影响。
6. 多系统、多项目或跨边界状态协作。

这些事项如果影响半径、迁移复杂度或回滚难度达到“重大实现”，则改按 `R3` 处理。

### 必须进入 R3 的条件

命中以下任一条件，必须覆盖五类视角：

1. 提案等级为 `architecture`。
2. 事项属于安全敏感。
3. 事项属于重大实现。
4. 用户明确要求完整五路或更高强度。
5. 更高优先级 system / developer 指令要求。

“安全敏感”指权限、认证授权、敏感数据、不可信外部输入、供应链或可被利用的 native/进程边界风险。并非所有原生调用都自动属于安全敏感。

“重大实现”指改变核心行为或架构边界、具有较大影响半径、涉及跨项目契约/迁移、难以快速回滚，或失败会显著影响运行与交付的实现。不得仅按目录名、文件数或代码行数判断；核心运行时、Source Generator、FrameBuild、CLI 中的局部低风险修改也不自动视为重大实现。

## 五类复盘视角

- 目标与约束：范围、需求、验收和非目标是否一致。
- 技术质量：正确性、结构、维护性、性能和错误处理。
- 安全：输入、权限、敏感数据、供应链和 native/进程边界。
- QA：可运行行为、用户流程、构建输出和集成边界。
- 上下文：历史决策、OpenSpec 一致性、跨模块约束和迁移兼容性。

`R3` 的五类视角都必须有独立证据与 verdict，但不要求五个代理，也不要求完整 `review-work`。

## Oracle 与 review-work 边界

### Oracle

当 `light` 仍处于本级范围，但包含多步骤技术推理、版本敏感事实或技术事实不确定性时，使用 `R1`。Oracle 可用时优先调用 Oracle；不可用时可由等价技术准确性复核替代，并在总结中记录原因、证据和 verdict。

### 完整 review-work

完整 `review-work` 是额外的外部工作流授权，不是 `R3` 的同义词。

- 不得因 `full`、`architecture`、安全敏感或重大实现标签自动调用完整 `review-work`。
- 用户明确要求“全面复盘”“完整 QA”或直接指定 `review-work` 时，可以启用完整 `review-work`。
- 用户直接指定 `review-work` 时，应按其工作流执行；工具不可用时必须说明，不能静默替换。
- 未获得上述授权但必须执行 `R3` 时，使用当前可用的专项检查组合覆盖五类视角。
- 更高优先级 system / developer 指令要求特定工具时必须遵守，并在总结中说明额外来源。

## 失败处理

- 任何测试、构建、静态检查或专业复核失败，都不得进入成功总结。
- 必须修复根因并重新执行受影响验证，或明确标记为阻塞/未完成。
- 一次失败本身不机械触发五路复盘；必须重新判定它是否揭示安全敏感、重大实现或提案范围扩大。
- 若失败揭示未批准的新范围，必须升级或修订 OpenSpec 并重新审核。
- 不得删除失败测试、降低断言或用“理论上可行”替代实际验证。

## 决策示例

### Fast 文案修正

执行读取、格式和路径检查，使用 `R0`，不调用审查代理。

### Light 版本敏感文档

执行直接来源核对，并增加 1 路技术准确性复核；Oracle 可用时优先使用 Oracle。

### Full 公共 API 变更

从目标约束、技术质量、QA、上下文等实际风险中选择 2-3 路，使用 `R2`。仅当它同时构成安全敏感或重大实现时才进入 `R3`。

### Architecture 治理文档

使用 `R3` 覆盖五类视角。用户未明确要求完整 `review-work` 时，不自动调用该工具。

### 安全敏感或重大实现

无论原默认强度如何，使用 `R3`。如果新事实扩大了已批准提案范围，还必须先修订提案并重新审核。

### 用户明确要求全面复盘或完整 QA

使用 `R3`，并允许启用完整 `review-work`；总结记录各视角结论、阻断修复与剩余风险。

## 文档同步策略

- `spec.md`：权威规范，使用 MUST / MUST NOT / SHALL / MAY。
- `AGENTS.md`：代理入口规则，提供三层模型、矩阵和门禁摘要。
- `openspec/README.md`：解释生命周期和三层模型。
- `proposal-levels.md`：记录默认强度、风险升级与工具授权。
- `review-checklist.md`：检查强度判定、Oracle 回退、`review-work` 授权与完成 Gate。

## 迁移路径

1. 先修订 change capability spec，固定权威语义并重新审核。
2. 获批后同步四个低优先级入口文档。
3. 用代表场景逐项核对一致性。
4. 对本 architecture 级治理实现执行 `R3` 五视角复盘，但不自动启用完整 `review-work`。
5. 新规则在本 change 完成实施、验证与总结后生效；历史完成项不追溯。

## 回滚策略

若三层规则造成遗漏或解释冲突，回滚本 change 对 capability spec、治理入口和模板的同步修改，恢复修订前规则。回滚不涉及运行时或数据迁移。

## 长期维护影响

- 未来治理更新必须同时检查提案等级、复盘强度和工具授权。
- 外部工具升级不会自动改变仓库政策，调整工具门禁需要另行治理审核。
- 目录名、代理数量和工具调用次数都不是风险或质量指标，验证证据与风险覆盖才是验收依据。
