# 分级实施后复盘治理规则

## 基本信息

- Change ID：`clarify-tiered-post-implementation-review-rules`
- 提案等级：`architecture`
- 状态：已实施并验证
- 请求来源：用户要求按 OpenSpec 等级与实际风险分层复盘，并进一步明确完整五路复盘与完整 `review-work` 的独立门槛。

## 背景

仓库已经定义 `fast`、`light`、`full`、`architecture` 四级提案、工件和总结深度，但实施后验证、专业复盘强度与审查工具之间仍存在边界歧义。上一版规则将 `architecture` 默认映射到 2-3 路专项复核，并允许一般风险触发器扩大到五路复盘；同时，完整五路复盘与外部 `review-work` 工具之间缺少明确的用户授权边界。

本次修订把治理模型拆为三个独立层次：OpenSpec 提案等级、实施后复盘强度、具体工具启用。五路复盘描述必须覆盖的风险视角，完整 `review-work` 描述一种外部执行工作流，两者不得再互相等同。

## 架构目标

- 保持 `design -> review -> implement -> test -> summarize -> commit` 生命周期不变。
- 明确 `review` 是实施前用户批准门禁，实施后验证与专业复盘属于 `test` 阶段。
- 将提案等级、复盘强度和工具启用建模为三个独立层次。
- 为四个提案等级提供可预测的默认复盘强度。
- 让安全敏感事项和重大实现独立触发完整五路复盘。
- 让公共契约、生成器/构建链、持久化、性能和跨系统协作等风险选择 2-3 路专项复核，而不是机械扩大为五路。
- 只有用户明确要求全面复盘、完整 QA 或直接指定 `review-work` 时，才启用完整 `review-work`；更高优先级强制指令除外。

## 非目标

- 不减少任何变更必须执行的测试、构建、静态检查或文档验证。
- 不允许用较低提案等级跳过安全、契约或失败验证所需检查。
- 不修改运行时代码、Source Generator、构建链、CLI 或 Projects 行为。
- 不修改 Oracle、`review-work` 或其他外部工具的实现。
- 不要求五个风险视角必须对应五个代理或五次工具调用。
- 不追溯重写已完成变更的审查记录。

## 规则摘要

实施后复盘强度使用以下有序等级：

- `R0 Direct`：直接测试、构建、静态检查或文档验证。
- `R1 Focused`：在 `R0` 基础上完成 1 个技术准确性视角的复核。
- `R2 Targeted`：在 `R0` 基础上完成 2-3 个与实际风险匹配的专项复核。
- `R3 Comprehensive`：在 `R0` 基础上覆盖目标/约束、技术质量、安全、QA、上下文五类视角。

默认映射为：

- `fast -> R0`
- `light -> R0`；仍属于 `light` 且复杂、版本敏感或技术事实不确定时使用 `R1`
- `full -> R2`
- `architecture -> R3`

安全敏感事项或重大实现无论原默认强度如何，都使用 `R3`。公共 API、生成器输出、配置/构建/发布契约、持久化、性能和跨系统协作等其他风险至少使用 `R2`；只有实际达到安全敏感或重大实现定义时才进入 `R3`。

完整五路复盘是一种审查强度，不等同于完整 `review-work`。`R3` 可以由可用工具组合完成，但不得仅因等级或风险自动启用完整 `review-work`。只有用户明确要求“全面复盘”“完整 QA”或直接指定 `review-work` 时，才允许启用完整 `review-work`；更高优先级 system / developer 指令要求时必须遵守。

`light` 的 `R1` 首选 Oracle 完成技术准确性复核。Oracle 不可用时，可以使用等价复核，但必须记录替代原因、证据和 verdict。

## 影响范围

正式实施阶段预计同步以下治理文件：

- `AGENTS.md`
- `openspec/README.md`
- `openspec/templates/proposal-levels.md`
- `openspec/templates/review-checklist.md`
- 本 change 的 `specs/repository-governance/spec.md`

全局项目影响：

- `War3Frame/`：无运行时行为变化，但未来变更受分层复盘规则约束。
- `War3Frame.Generator/`：无生成器行为变化；生成契约变更至少进入 `R2`，重大生成契约迁移进入 `R3`。
- `FrameBuild/`：无构建行为变化；普通构建/发布契约变更至少进入 `R2`，重大链路重构进入 `R3`。
- `CSharpWar3Frame/`：无 CLI 行为变化；普通契约变更进入 `R2`，重大主流程调整进入 `R3`。
- `Projects/`：无示例或测试行为变化；跨项目验证风险用于选择 `R2` 专项，重大跨项目迁移进入 `R3`。

## 候选方案比较

### 方案 A：所有实现统一五路复盘并调用 `review-work`

覆盖面固定，但例行变更耗时高，也把风险强度与工具绑定，不采用。

### 方案 B：只按 OpenSpec 等级决定复盘强度

规则简单，但无法处理低等级变更中后来发现的安全或重大实现风险，不采用。

### 方案 C：提案等级、复盘强度、工具授权三层判定

默认成本可控，风险可以独立升级，同时保留用户对完整外部工作流的明确授权边界；采用此方案。

## 阶段拆分

1. Phase 1：修订本 change 的 proposal、design、tasks 与 capability spec，并重新提交用户审核。
2. Phase 2：获批后同步 `AGENTS.md`、README、提案模板和审核清单。
3. Phase 3：用代表场景检查各文档结论一致，完成 `R3` 五视角复盘和架构级总结。

## 迁移与兼容

- 修订后的规则只在本 change 完成实施与验证后生效。
- 在重新获批前，已同步到入口文档的上一版规则仍视为待修订状态，不继续扩大修改范围。
- 既有 OpenSpec 等级、工件矩阵、用户批准门禁和总结深度保持不变。
- 已批准但尚未完成 `test` 的在途 change 使用新规则的最低强度，但不得降低用户已经明确要求的更高强度。
- 历史已完成变更不追溯重做复盘。
- 仓库规则不覆盖更高优先级的 system / developer 强制指令；额外审查来源必须在总结中说明。

## 风险与回滚

- 风险：协作者把减少工具调用误解为减少测试。缓解：规范明确 `R0` 在所有等级都必须执行。
- 风险：五路复盘与完整 `review-work` 再次混用。缓解：分别定义强度门槛和工具授权门槛，并加入正反场景。
- 风险：`light` 绑定 Oracle 导致工具不可用时阻塞。缓解：Oracle 为首选，允许有记录的等价技术准确性复核。
- 风险：“重大实现”被按目录名或代码行数机械判断。缓解：以核心行为、影响半径、迁移复杂度和回滚难度定义。
- 风险：多份治理文档表述漂移。缓解：change capability spec 为权威来源，其余文件镜像同步。
- 回滚：恢复本 change 和四个治理入口文件到修订前状态；不涉及代码或数据迁移。

## 验收标准

- 仓库文件明确区分提案等级、复盘强度和工具启用。
- `fast` 使用 `R0`；`light` 默认 `R0`，复杂或版本敏感时使用 `R1`；`full` 使用 `R2`；`architecture` 使用 `R3`。
- 安全敏感事项和重大实现独立触发 `R3`。
- 普通公共契约、生成器/构建链、持久化、性能和跨系统风险不会仅因分类名称自动触发 `R3`。
- Oracle 是 `light/R1` 技术准确性复核的首选工具，并具有明确回退规则。
- 完整五路复盘不自动等同于完整 `review-work`。
- 只有用户明确要求全面复盘、完整 QA、直接指定 `review-work`，或更高优先级指令要求时，才启用完整 `review-work`。
- `AGENTS.md`、README、模板、checklist 与 capability spec 无冲突。
- 所有运行时、生成器、构建、CLI 与 Projects 文件保持不变。

## 审核门禁

本修订提案必须获得用户重新明确批准，之后才能同步修改生效治理文件。实施中若发现需要改变 OpenSpec 等级制度、用户批准门禁或外部工具实现，必须停止并重新提交扩展提案。
