# 定义 War3 Native 硬件输入 Tag 处理规范

## 0. 基本信息

- Change ID: `define-war3-native-input-tags`
- 提案等级: `light`
- 目标一句话: 为后续 War3 Native 硬件输入接入定义 ECS Tag / Event / State 的建模规则，避免同类型组件覆盖和输入语义混乱。
- 请求来源: 用户提出 Q/E 等硬件按键按下与抬起事件应由 `war3Native` 创建和清理 Tag，并要求先生成提案供后续实现读取。

## 1. 分级判定

### 1.1 为什么是 light

- 影响范围: 未来会影响 `War3Frame/` 内输入组件、输入 Native 桥接系统和输入映射系统；当前只记录设计约束。
- 风险等级: 中低；本提案不直接实现运行时代码，不改变现有行为。
- 可逆性: 高；若后续实现前发现 War3 输入 API 约束不同，可调整提案或另开变更。
- 是否跨项目: 当前不跨项目；后续示例绑定输入时才影响 `Projects/`。
- 是否改公共契约: 当前只定义规范，不立即新增公共 API；后续正式实现输入组件/系统时需要按实际范围补充任务或升级。

## 2. 背景与目标

硬件输入会同时存在瞬时事件和持续状态：例如 Q 键按下、Q 键抬起、Q 键当前按住。若把多个 `KeyInputEvent` 作为同类型组件写到同一个玩家输入实体，Q/E 同帧输入会互相覆盖；若只用事件表达按住状态，又难以处理持续施法、长按蓄力、移动按住等场景。

目标是约定后续输入接入时的分层与生命周期：

- War3 Native / Input Native 层负责捕获硬件输入，并写入 ECS 原始输入状态或瞬时事件。
- “按下中”使用可跨帧存在的 State Tag 或 State Component 表达。
- “抬起”使用只存在一帧的 Event Tag 或事件实体表达，消费后清理。
- 业务系统不直接依赖 Q/E 等硬件键，而消费映射后的语义请求。

## 3. 影响范围

- 模块: 未来主要影响 `War3Frame/` 的输入组件、Native 输入桥接、输入映射和业务请求生成。
- 文件: 本提案仅新增 OpenSpec 记录；后续实现可新增 `Input` 相关 components / systems。
- 不受影响区域:
  - `War3Frame.Generator/`: 当前不新增系统注册实现，不影响生成器。
  - `FrameBuild/`: 不影响构建链路。
  - `CSharpWar3Frame/`: 不影响 CLI。
  - `Projects/`: 当前不新增示例绑定；后续若加入 Q/E 施法示例再单独纳入验证。

## 4. 方案摘要

### 4.1 输入分层

后续实现采用三层数据流：

1. `War3NativeInputSystem` 或同类 Native 层系统捕获 War3 硬件输入。
2. 输入状态层维护按键当前状态，并发出瞬时边沿事件。
3. `InputMappingSystem` 把硬件输入映射为 `CastRequest`、移动请求、选择请求等业务语义请求。

业务系统不得直接查询 `QKeyDownTag` 这类硬件细节，避免键位绑定侵入技能、移动、交互流程。

### 4.2 按下状态建模

按键按下后，Native 输入层可以在对应玩家/按键状态实体上添加“按下中”状态，例如：

- `KeyPressedStateTag`
- 或携带键码、玩家、时间戳的 `KeyInputState` 组件。

该状态允许跨帧存在，直到收到对应抬起事件后由输入层移除或更新。Q/E 同时按下时，不应把两个同类型组件写在同一个实体上；可使用每个玩家每个按键一个状态实体，或在玩家输入状态组件中维护按键集合。

### 4.3 抬起事件建模

按键抬起时，Native 输入层应：

1. 删除或更新对应的“按下中”状态。
2. 生成“抬起”瞬时事件，例如 `KeyReleasedEventTag` 或 `KeyInputEvent(phase: Released)`。
3. 保证抬起事件只存在一帧或一个输入处理周期，由输入映射系统消费后清理。

“抬起”不应作为长期状态保留；否则业务系统会误判后续帧仍处于释放事件。

### 4.4 同帧多键输入

同帧 Q/E 同时按下时，应保证事件不会覆盖：

- 原始瞬时输入推荐“一条事件一个实体”。
- 持续状态推荐“每玩家每按键一个状态实体”或“玩家输入状态组件持有按键集合”。
- 不允许把多个不同按键的同类型 `KeyInputEvent` 组件连续写入同一个实体。

### 4.5 语义请求输出

输入映射层根据配置或固定绑定把硬件输入转为业务请求，例如：

- Q 按下 -> `AbilityInputRequest(slot: 0)` 或直接生成合法的 `CastRequest`。
- E 按下 -> `AbilityInputRequest(slot: 1)`。
- 右键点击 -> 移动或攻击请求。

后续若引入手柄、UI 点击、AI 自动施法，也应复用同一业务请求入口。

## 5. 风险与回滚

- 风险: War3 原生输入 API 对按下/抬起捕获能力可能有限，实际实现时需要按可用事件调整系统边界。
- 风险: 若过早把硬件键位暴露给业务系统，会造成键位重绑困难。
- 控制: 本提案只约束后续实现方向；真正实现前读取 War3 Native 输入 API 和现有系统注册模式。
- 回滚方式: 删除或调整该提案，不影响当前运行时行为。

## 6. 验收标准

- 明确按下状态与抬起事件的生命周期差异。
- 明确按下状态可跨帧存在，抬起事件只存在一帧或一个输入处理周期。
- 明确 Q/E 同帧输入不得因同类型组件写入同一实体而互相覆盖。
- 明确 Native 输入层只负责捕获硬件输入并写 ECS 状态/事件，业务层消费映射后的语义请求。
- 后续实现硬件输入时，应先读取本提案并据此补充具体组件、系统和验证任务。
